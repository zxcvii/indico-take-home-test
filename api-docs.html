High-throughput inventory reservation for flash-sale events.

REST API for atomically reserving limited product inventory under high concurrency, confirming reservations, and querying real-time stock.

Reservation lifecycle

A successful reserve moves quantity from available into reserved for a 5-minute TTL. If not confirmed within the TTL, the held quantity is automatically returned to available stock by a background sweeper (and is additionally treated as expired on read).

Physical inventory (total_stock) is decremented only on confirm.

Concurrency guarantees

Reserving is performed with a single atomic conditional UPDATE in PostgreSQL, so requests never over-sell stock nor drive it negative. A concurrent or repeated confirm is idempotent: only the first transition out of ACTIVE succeeds.

Error model

Every non-2xx response uses a single envelope (Error) with a stable, machine-readable error.code, a human-readable error.message, and optional structured error.details.

Authentication

Authentication is out of scope for this service: user_id is a trusted, client-supplied identifier. No security scheme is required (see the root-level security: []). A production deployment would derive user_id from an authenticated session.

Reserve stock

Atomically reserve inventory for a user if sufficient available stock exists. The reservation expires after 5 minutes unless confirmed.

Request Body schema: application/json
required
user_id
required
string non-empty

Identifier of the user requesting the reservation.

item_id
required
string non-empty

Identifier of the item to reserve.

quantity
required
integer <int32> >= 1

Number of units to reserve. Must be at least 1.

Responses

Confirm reservation

Permanently commit an active reservation, completing the order process and decrementing physical inventory. Idempotent: only a reservation in the ACTIVE state can be confirmed.
